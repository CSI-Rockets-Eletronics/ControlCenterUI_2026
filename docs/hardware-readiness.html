What's new

What the new UI does differently with the data

Almost all of the redesign is visual. These are the only changes in how the UI reads data or sends commands, so they're what Wednesday actually tests.

  • Cap-fill labels fixedThe old UI showed raw pF under "Height (%)" and the percent under "Capacitance". Now each is labeled correctly.
  • QD removed, Pilot "Sensor off"The QD sensor is gone, so QD is no longer shown. Pilot is sent as a hard-coded 0 (same as last year) and is labeled "Sensor off" instead of showing it as a reading.
  • Two dead commands removedDOME_PILOT_OPEN and EREG_SET_GAINS had no number in firmware or the Pi script; nothing could have sent them anyway.
  • Reconnects on its ownAfter a failed request the UI retries every second instead of waiting for a dismiss.
  • Stale data shows as staleCharts only plot new records, so a dead link shows as a gap and the header shows the connection state, instead of a flat "live" line.
  • FIRE always needs armingThe old Command center's unarmed FIRE button is gone.

ABORT does not close valves opened from Manual relay control

What happens

When the UI's Manual relay control sends STATE_CUSTOM, the firmware remembers four valves as "manual overrides": GN2 Drain, GN2 Fill, LOX Fill and LOX Disconnect. It keeps them on in every state, ABORT and STANDBY included. 

// dev_fs_relays.h, end of UpdateRelayStates()
relay_states.gn2_fill = relay_states.gn2_fill || manual_gn2_fill;
relay_states.lox_fill = relay_states.lox_fill || manual_lox_fill;
// ... same for gn2_drain, lox_disconnect

// UpdateCustomRelayStates(): "persist when leaving CUSTOM state"
manual_gn2_fill = command_packet.gn2_fill;

So: open GN2 Fill manually, press ABORT, and GN2 Fill stays open.

Decision

ABORT should close every manual valve and leave only depress open. Confirmed by the team on 2026-11-13.

Fix status

Written in draft PR avionics-software-2026-2027#2 (branch fix/abort-clears-manual-overrides, commit 1cee64b): ABORT clears the four manual overrides. Other states are unchanged.

Not compiled or flashed yet. Until a board runs it, the firing station behaves the old way. The simulator already has the fix (commit d435bd9), so it shows the new behavior.

What's missing

A build, a flash and one bench check: relays disconnected, open GN2 Fill from Manual relay control, send ABORT, confirm only depress is on.

Actions
  • Flash PR #2 and bench-check it, ideally before Wednesday.
  • Until it's flashed: after any manual relay use, switch each manually opened valve back off in Manual relay control before relying on ABORT. Turning a valve off there clears its override, because the next STATE_CUSTOM rewrites all four flags.
  • Optional, later: add the four override flags to the FsState packet so the UI can show "Manual override active". Needs a packet change in firmware, Pi script and UI together.

LOX level percent is self-scaling

Context

This is not new and not caused by the UI work. dev_cap_fill.h is byte-for-byte the same as last year's (avionics-software-2025-2026, last changed 2026-04-29 before cold flow). The probe and board work; only the conversion to a percent is approximate.

What happens

The board turns probe capacitance (pF) into a percent using a fixed "empty" value and the highest reading seen since boot as "full". That's a deliberate shortcut: it needs no full-tank number, and it reads correctly once the tank has been filled since boot. 

// dev_cap_fill.h, CapacitanceToHeightPercent()
const float kMinCapacitance = 259.074219;  // empty, pF
if (probe_cap_pf > max_capacitance_pf) max_capacitance_pf = probe_cap_pf;
height_percent = (probe_cap_pf - kMinCapacitance) / (max - kMinCapacitance) * 100;

The catch: while the tank is filling, each new reading is the new maximum, so the percent sits near 100% the whole way up. With an empty tank right after boot it reads noise. After a fill (holding, or draining) it is accurate.

Already fixed (UI)

The old UI had the two field labels swapped: the chart called "Cap Fill Height (%)" was plotting raw pF, and "Capacitance" was plotting the percent. That's why the numbers may never have looked right. The new UI reads cap_fill_base as the level and clamps it to 0–100 on the P&ID. Confirmed against the Pi script.

What's needed

Nothing for Wednesday. No special LOX fill is needed to calibrate: if the tank gets filled during normal operations anyway, just note the capacitance empty and full.

Actions
  • Watch the capacitance, not the percent, during a fill. "Cap Fill Capacitance" (pF) on the Data display rises directly with level and needs no calibration.
  • Whenever a fill happens anyway: jot down the pF reading empty and full. With those two numbers, firmware can use a fixed scale and clamp to 0–100.

Where do load cell and radio data come from?

Load cells

From the load-cells-futek repo (private, readable with team access). It runs on the same Pi as the firing station, as its own service (run.sh), and uploads to the same data server with the same settings the UI reads: 

# load-cells-futek/run.sh
python write_records.py http://localhost:3000 0 LoadCell1
python write_records.py http://localhost:3000 0 LoadCell2

Same server (localhost:3000 on the Pi), same environment key (0, same as the firing station script), device names LoadCell1 / LoadCell2, and each record is a plain number in lbs, which is exactly what the UI expects. Last change 2026-04-29 (Aruzhan).

Radio

RadioGround isn't produced by anything in these repos. It's rocket radio telemetry (GPS altitude, acceleration), so the Altitude and Acceleration cards will be empty on a ground test. That's expected.

Actions
  • Wednesday: make sure the load cell service is running and both FUTEK USB units are plugged into the Pi. If the Load Cells chart stays empty, check that service first.
  • Nothing needs to be made public. If the repo is opened up anyway, it's worth a quick look for anything that shouldn't be public first.

Pilot pressure isn't read

From office hours

The QD pressure sensor no longer exists, so QD has been removed from the UI completely. The pilot pressure transducer is still installed; getting it read again is hardware/firmware work for Aruzhan.

What happens
// dev_fs_lox_gn2_transducers.h
//pilot_pres.Tick();  // DISABLED
.pilot_pres = 0.0f,  // DISABLED - pilot_pres.GetLatestPsi(),

A likely reason it was turned off: the commented-out pilot config uses the same ADC as COPV 1 (bus i2c3, address VIN, channel 0). Two sensors can't share that one input, so pilot probably needs its own ADC channel or address.

Already done

The UI drops the hard-coded 0 and shows "Sensor off" on the P&ID, its Pilot graph and the Data display. The header's pilot over-pressure warning can't fire on it either.

What's needed

Wire pilot to a free ADC input, update its config in firmware, and re-enable the read. Then remove pilot_pres_psi from DISABLED_SIGNALS in src/stores/telemetryStore.ts and it shows up everywhere again.

Run order for the first live session

Each step only starts once the previous one checks out.

  1. Relays disconnected. Valves unplugged, or LEDs on the relay outputs. Igniter disconnected.
  2. Open the UI against the Pi. No ?server=, or the production build on the Pi. Header shows CONNECTED and LIVE HARDWARE; FS uptime counts up.
  3. Watch every value move. COPV, Oxtank, injector, thermocouples, cap fill, relay currents. Pilot shows "Sensor off" (expected; there is no QD anymore). Load cells show data if their service is running (see open items); Altitude and Acceleration stay empty on a ground test.
    Stop if the header shows a server error: some record doesn't match what the UI expects.
  4. Send each state command once from Firing control and confirm the station state and relay dots change, and match the ESP32 serial log.
  5. Test Manual relay control, then switch everything back off by hand before pressing ABORT. Confirm only depress is on. (If PR #2 has been flashed, also try ABORT with a manual valve still open: it should close.)
  6. Note the cap-fill capacitance with the tank empty. Optional; useful later for a fixed scale.
  7. Only then reconnect valves.
